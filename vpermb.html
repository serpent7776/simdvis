table
Notes
  • Operand order. Intel syntax is VPERMB dst, idx, table: the indices are the first source (EVEX.vvvv, always a register) and the table is the second (ModR/M r/m, so it can come straight from memory). The intrinsic keeps that order: _mm512_permutexvar_epi8(idx, table). AT&T syntax reverses it: vpermb table, idx, dst.
  • Lanes don't matter. Unlike PSHUFB, which shuffles within each 128-bit lane, every destination byte can take any table byte. The orange dot on a dst byte marks one that came from another lane.
  • Only the low log2(N) index bits are used: bits [3:0] for XMM, [4:0] for YMM, [5:0] for ZMM. The rest are ignored, so indices wrap around the table.
  • Bit 7 does not zero. PSHUFB writes 0 where the index has bit 7 set; VPERMB ignores bit 7. To get the same effect use zero-masking, e.g. vpmovb2m k1, idx then knotq k1, k1 and vpermb dst{k1}{z}, idx, table.
  • No embedded broadcast (bytes have no {1toN} form), and there is no VEX or legacy encoding: it is EVEX-only.
  • Bits above the vector length are zeroed, as for every EVEX instruction.
  • For 128-entry lookups across two tables use VPERMI2B / VPERMT2B, which use 7 index bits. The 16-, 32- and 64-bit element versions are VPERMW, VPERMD and VPERMQ.
  • A full ZMM table holds 64 entries, exactly the base64 alphabet. That makes VPERMB the lookup step of AVX-512 base64 encoders: a byte shuffle and VPMULTISHIFTQB cut 48 input bytes into 64 six-bit fields, one per byte, leaving junk in bits 7:6. VPERMB ignores those bits, so it turns the fields into characters with no masking step. Try the base64 preset.
  • Requires AVX512_VBMI (CPUID.(EAX=07H, ECX=0):ECX[1]), plus AVX512VL for XMM/YMM. Intel since Cannon Lake / Ice Lake, AMD since Zen 4.
